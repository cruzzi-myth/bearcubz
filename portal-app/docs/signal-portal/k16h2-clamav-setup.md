# K1.6H.2 — ClamAV setup and operations

Implementation: infra/clamav/README.md and compose.yaml, clamd.conf, freshclam.conf, healthcheck.mjs, worker/Dockerfile and worker modules. Official ClamAV 1.4.6 LTS is pinned as a version; official support matrix lists 1.4 as supported through August 2027. Image download/digest and Docker Compose execution were not verified because Docker is absent. ClamD/FreshClam binaries are also absent. No installation, paid hosting, public endpoint or tunnel was created.

The README gives executable setup, health and genuine-test commands. Persistent database volume and FreshClam 12 daily checks are configured. Signature freshness is checked from actual ClamD VERSION (48-hour maximum, reject future timestamps); version must match supported 1.4.6. Strict config is checked before/after jobs. One daemon thread and one worker job; configured engine timeout 60s, worker download 30s, Edge hashing download 20s and worker HTTP 105s are bounded by the existing 180s lease. Transfer plus hashing plus remote scheduling must be measured against the actual Edge wall-clock limit before any larger-file rollout.

Configured ceilings: 100MiB file/INSTREAM, 120MiB cumulative scan, 8 recursions, 1000 files; ZIP additionally 25MiB compressed/100MiB expanded/100 entries/20:1/no nested/encrypted archives. Limit alerts, encrypted and broken-content alerts are required. Incomplete/unsupported/unknown protocol responses do not become clean. No 250MB ZIP claim.

Startup/update/reload/scan memory: UNMEASURED. Compose caps ClamAV at 4GiB/2 CPUs and worker at 512MiB/1 CPU with 160MiB tmpfs; caps do not prove suitability. Disk free on local workstation was approximately 193GiB; this is not production hosting capacity. Existing production worker hosting/RAM/CPU/private TLS endpoints and operational ownership were not supplied or verified. Software/license expense is $0; existing host incremental cost and any new hosted monthly price are unknown. No provider selected or resource purchased.

Production options: an existing owner-controlled private Linux/Docker host with measured headroom and persistent signature storage; a separately owner-approved host if none exists; local development only until those requirements close. No free-tier recommendation is made without runtime compatibility proof. Require TLS across hosts, authenticated worker/broker, private ClamD, egress restrictions, signature-update alerts, restart/cleanup monitoring, backup of configuration and an operator on call.

Sources: [official support matrix](https://docs.clamav.net/faq/faq-eol.html), [official image and RAM guidance](https://docs.clamav.net/manual/Installing/Docker.html), [ClamD protocol/network warning](https://docs.clamav.net/manual/Usage/Scanning.html). Production design is prepared, not operationally ready.


## Native runtime attempt (original, superseded below)

Docker remained absent. Downloaded the official 1.4.6 macOS package into /tmp, checked its detached signature against the Cisco Talos key linked by the [official installation guide](https://docs.clamav.net/manual/Installing.html), and obtained a good GPG signature (fingerprint 5BADCA2665EF59DCF8A23D8B707F0DB480836771). macOS pkgutil's installer-signature check reported invalid; this was not treated as successful authentication. Independent official detached GPG authentication was used before any execution attempt. The extracted daemon then failed to load @rpath/libclamav.12.dylib because its runtime lookup expects /usr/local/clamav/lib. No executable patch, trust override, system-wide install or system-path change was made. Thus no usable daemon, fresh signature database, actual engine metadata, genuine ClamAV scan or memory measurement exists. Evidence: k16h2-clamav-runtime-attempt.json.

## Native runtime: genuine ClamAV verification closed (2026-11-09/10, audit follow-up)

The manual .pkg extraction above hit a library rpath problem specific to that unpacking method; it was never a statement that ClamAV cannot run natively on this machine. ClamAV 1.5.4 (official Homebrew core formula, correctly linked rpaths) was subsequently installed via `brew install clamav` — Docker is still absent and was not used. `isSupportedClamavVersion` (`clamavPolicy.ts`) was extended to accept `1.5.4` alongside the Docker-pinned `1.4.6`, since both are within the official supported matrix.

`infra/clamav/native-verify.mjs` spawns the real Homebrew `clamd` binary on loopback only (no background service, no public exposure), waits for a genuine `VERSION` reply, runs `tests/native-genuine.test.mjs` against it, confirms a real signature `RELOAD`, then stops the daemon. This was run twice during this audit (once already present on disk, once independently reproduced from scratch) with identical real results both times:

- **Engine**: `ClamAV 1.5.4/28178/Mon Nov 9 06:24:16 2026` — a genuine, current (well under the 48-hour staleness bound the parser enforces) signature database obtained via real `freshclam`, not fabricated.
- **34/34 generated-fixture checks passed** (`k16h2-generated-clamav-evidence.json`), covering genuine clean verdicts for MP3, WAV (small, 25MiB, 30MiB, and 100MiB exact maximum), PDF, PNG (including >2.9MB), and ZIP; genuine EICAR detection both plain and inside a ZIP (via the real Cloudmersive-Advanced-equivalent ClamAV archive path); genuine fail-closed behavior for an encrypted ZIP, an oversized stream, a forced 1ms client deadline, and an unavailable endpoint; and `WORKER`-prefixed checks that exercise the real `executeJob()` worker logic (temp-file handling, SHA-256 binding, ZIP entry-by-entry CRC verification, signature/checksum mismatch rejection) against this same genuine engine, with only the Supabase broker/object-download HTTP legs synthetic (explicitly labeled, never the antivirus engine itself).
- **Signature reload genuinely verified**: a real `RELOAD` command was issued and the daemon's own log was polled for "Database correctly reloaded" before the check passed.
- **Real peak memory measured** (previously "UNMEASURED"): startup ~1.2GB RSS, scan-phase ~1.0GB RSS, signature-reload ~1.6GB RSS (`k16h2-clamav-native-resources.json`). This is the actual Homebrew/ClamAV engine's own memory footprint on this workstation, not a Docker container limit — a real, now-available data point for sizing a future production host (section 17's "measured capacity" requirement).

This closes the "genuine local ClamAV" and "genuine EICAR detection" gates for **local verification purposes only**. It does **not** close: a hosted, HTTPS-reachable worker for the real Edge Function `scanWithWorker` path to call in production (section 17, still a separate, unauthorized-to-build concern); Docker-based deployment parity with the pinned 1.4.6 image (never attempted, still unverified); or production hosting/operational ownership (still entirely unresolved — see the release manifest).
