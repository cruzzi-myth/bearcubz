# K1.6H.2 — Scanner security

## Trust and exact-byte binding

Artists supply neither scanner results nor worker URLs/tokens. Existing artist table privileges still deny UPDATE. New asset defaults require security. Worker only accepts object kind, object UUID and attempt UUID under a dedicated >=32-character bearer token; unknown fields/paths/URLs are rejected. A separate Edge broker verifies scanning state, active row, current attempt, expected server-computed checksum and at least 90 seconds of lease, then issues a 90-second signed read capability. Worker has no service-role key; broker retains the existing trusted service client. Risk: that broker has broad server storage privileges, and the dedicated worker token can retrieve eligible in-flight jobs whose IDs it knows. It cannot mint arbitrary path URLs or write clean verdicts directly. Protect and rotate it like a server credential.

The coordinator streams/hashes object bytes with an exact length limit; large input is not buffered in Edge. Worker independently streams to a private temporary file, verifies exact length/SHA, validates actual signature and archive policy, then uses ClamD INSTREAM. No redirects or foreign hosts are accepted. Only the same attempt can write back. Clean worker results require provider/policy/size/hash/attempt match, supported engine, fresh real signature version/time, valid timestamps and complete=true/withinLimits=true. Unknown metadata is null, never invented. Returned results arrive on the authenticated worker request; there is no artist-callable result callback.

Small eligible bytes keep the existing Cloudmersive API. Local EICAR interception is labeled eicar-test-fixture, not engine evidence. Cloudmersive does not return engine/signature versions in this integration: fields remain null. No automatic provider fallback exists; enabling fallback=true is rejected. Missing/invalid configuration, worker failures and incomplete scans fail closed. Artist cap stays 2,900,000; default routing is Cloudmersive-only.

## Release gates

Attachments still need clean plus artistic review approval and final-bucket promotion. Newly created rows additionally require exact-byte evidence before available. Existing legacy attachment rows remain identifiable by scan_evidence_required=false; no future endpoint creates such an exemption. Administrator assets require security_required=true, clean complete evidence matching current SHA/size/attempt, thumbnail evidence if applicable, and separate security review identity/time before upload_status=ready. Database trigger blocks readiness and downgrade; released object path/checksum cannot be swapped. Only trusted server components may write evidence. Existing broad service-role authority is not cryptographic proof that a provider was called; production must restrict server deployment and retain audit records.

Legacy assets are explicitly legacy_unverified, retain availability and retain pending artwork approval. They are NOT assigned fake clearance. Explicit revalidation preserves legacy availability on scan failure; conversion to the new enforced gate requires successful scan and explicit security release review. Production has no assets; do not import the legacy exemption as a transfer shortcut.

## Completeness and runtime limits

K1.6G metadata ZIP validator is retained. Worker additionally reads every supported ZIP entry under CPU/address-space/expanded-byte bounds, checks CRC/length and rejects decompression failure. It extracts nothing. ClamAV then scans the complete container with strict limit/encryption/broken-content alerts. Only exact stream: OK can be clean; limit/skipped/error/unknown replies cannot. Config checks do not attest a hostile daemon: the daemon/runtime/network are trusted infrastructure and must be verified together before activation. **Audit follow-up (2026-11-09/10):** genuine engine proof and near-limit processing (a 100MiB-exact WAV, high-ratio/nested/encrypted/corrupt ZIP entries, a forced client deadline, an unavailable endpoint) have since been verified against a real local Homebrew ClamAV 1.5.4 daemon on loopback, reproduced twice — see `k16h2-clamav-setup.md`. This proves the local engine and worker logic genuinely work; it does not verify the daemon/runtime/network trust boundary for a real hosted production worker, which remains unestablished.

## Cost controls

Existing three-attempt auto limit is now checked atomically in the claim RPC; a separate service-role-only manual claim wrapper retains the audited exception. Recovery remains five rows/run with backoff; no fallback loop. New portal_scanner_usage records application-observed primary outcomes by attempt/provider. It is NOT the Cloudmersive account total and does not include other callers or separate thumbnail requests. Admin status labels that scope and actualProviderUsage=null; key presence is not an operational scan. No global account quota is invented. Genuine Cloudmersive calls in H2 use generated fixtures; successful scans are not automatically repeated.
